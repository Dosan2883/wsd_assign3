## 🚀 빠른 실행 방법

Node.js 18 이상과 npm이 필요합니다. 별도 데이터베이스나 환경변수 설정은 필요하지 않습니다.

```bash
# 1. 저장소 다운로드
git clone https://github.com/Dosan2883/wsd_assign3.git
cd wsd_assign3

# 2. 잠금 파일 기준으로 의존성 설치
npm ci

# 3. 서버 실행
npm start
```

브라우저에서 http://localhost:3000 에 접속합니다. 서버 종료는 터미널에서 Ctrl+C를 누릅니다.

`node_modules`는 제출에 포함하지 않습니다. `npm ci` 실행 시 `package-lock.json`에 기록된 의존성이 설치됩니다.

## 📂 파일 구성 및 엔지니어링 특징

### 1. `server.js` (Express 백엔드 API)
- **대량 데이터셋**: 1,000건의 인메모리 게시글 데이터 자동 시드.
- **방어적 파라미터 파싱**: `parseInt(..., 10)` 기수 명시, 음수 및 0 페이지 차단, `Math.min(..., 100)` 대량 조회 공격 방어.
- **ORDER BY 화이트리스트 보안**: `SORT_WHITELIST` 객체 매핑으로 SQL Injection 원천 봉쇄 및 `id DESC` 동점자 방지 2차 정렬 결합.
- **2대 페이징 API 제공**:
  - `GET /api/posts`: 오프셋 기반 페이징 (`LIMIT` / `OFFSET`, 표준 `meta` Envelope 응답)
  - `GET /api/posts/cursor`: 고성능 커서 기반 페이징 (`WHERE id < ? ORDER BY id DESC LIMIT 10`, `limit + 1` 패턴으로 `COUNT(*)` 제거)

### 2. `index.html` (SPA 프론트엔드 & 실시간 DevTools 검사기)
- **탭 모드 전환**: [오프셋 번호 페이징] ↔ [커서 기반 무한 스크롤] 즉시 비교.
- **실시간 디바운스 (300ms)**: 연속 타이핑 시 불필요한 API 요청 폭격 방지.
- **AbortController 비동기 방어**: 새 검색어 입력 시 이전 진행 중인 fetch 요청을 즉각 취소하여 Race Condition 버그 예방.
- **브라우저 히스토리 동기화**: `URLSearchParams`와 `history.pushState` 및 `window.onpopstate` 이벤트로 뒤로 가기 / 새로고침 상태 복원 지원.

## 실습 핵심 개념

### 1. 오프셋과 커서에 적합한 화면

오프셋 방식은 페이지 번호로 특정 위치에 이동하는 게시판, 검색 결과 목록, 관리자 목록에 적합합니다. 검색 결과의 전체 개수와 전체 페이지 수를 보여 주기 쉽습니다. 데이터가 추가되거나 삭제되어 앞쪽 항목의 위치가 바뀌면 페이지 사이에 누락이나 중복이 생길 수 있습니다.

커서 방식은 마지막으로 읽은 항목을 기준으로 다음 묶음을 조회하므로 피드, 무한 스크롤, 더 보기 화면에 적합합니다. 이 실습에서는 ID 내림차순을 사용하며, 다음 요청에 마지막으로 반환한 ID를 전달하여 그보다 작은 ID를 조회합니다. 특정 페이지 번호로 곧바로 이동하려면 별도의 기준점이 필요합니다.

### 2. 디바운스와 요청 취소의 역할

디바운스는 입력할 때마다 예약된 실행을 취소하고 다시 예약하여 요청 횟수를 줄입니다. 이 실습에서는 마지막 입력 이후 300ms 동안 새 입력이 없을 때 검색 요청을 보냅니다. 따라서 입력 간격이 300ms 미만인 연속 타이핑은 마지막 검색어에 대한 한 번의 요청으로 합쳐집니다.

요청 취소는 이미 전송되어 진행 중인 요청을 중단합니다. 검색어가 바뀌면 AbortController의 abort()를 호출하고, AbortError는 정상적인 취소로 처리합니다. 응답을 반영하기 직전에도 현재 요청인지 검사하여 오래된 응답이 최종 결과를 덮어쓰지 않게 합니다. 디바운스는 요청 빈도를 줄이고, 요청 취소와 현재 요청 검사는 비동기 결과의 일관성을 지킵니다.

### 3. limit + 1 원리

커서 API는 검색 조건과 커서 조건을 모두 만족하는 항목을 최대 limit + 1개 찾습니다. 한 페이지의 한도가 10개일 때 11개를 찾았다면 다음 항목이 있으므로 hasNext를 true로 설정하고, 응답에는 앞의 10개만 담습니다. 다음 커서는 실제로 반환한 10번째 항목의 ID입니다. 추가로 확인한 11번째 항목은 다음 요청에서 반환할 수 있습니다.

조건에 맞는 항목이 10개 이하이면 hasNext는 false입니다. 이 방식으로 전체 결과 수를 세지 않고도 더 보기 가능 여부를 판단할 수 있습니다. 현재 코드가 배열을 순회하는 비용과 실제 데이터베이스 인덱스의 탐색 비용은 구분하여 해석하며, 응답 시간은 실습 환경의 관찰값으로 기록합니다.

### 4. offset과 totalPages 계산식

page는 1부터 시작하고, limit은 한 페이지의 최대 항목 수이며, totalCount는 검색 조건에 맞는 전체 항목 수입니다.

```javascript
// 기본 계산식
offset = (page - 1) * limit;
totalPages = Math.ceil(totalCount / limit);

// 이 실습 코드의 빈 결과 및 마지막 페이지 초과 처리
totalPages = Math.max(1, Math.ceil(totalCount / limit));
safePage = Math.min(page, totalPages);
offset = (safePage - 1) * limit;
```

예를 들어 page가 3이고 limit이 10이면 offset은 20이므로 정렬된 결과의 21번째 항목부터 조회합니다. totalCount가 83이고 limit이 10이면 전체 페이지는 9개이고 마지막 페이지에는 3개가 남습니다. 이 실습은 결과가 0건인 경우 빈 목록을 1페이지로 표시합니다. 계산 전에 잘못된 page는 1로 보정하고 limit에는 기본값과 상한을 적용합니다.
